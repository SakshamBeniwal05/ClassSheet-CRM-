================================================================================
                           CLASSSHEET CRM - SYSTEM DESIGN
================================================================================

1. ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------
CallSheet is an enterprise-grade CRM platform featuring a decoupled architecture:
- Frontend: Single Page Application (SPA) built with React 18, TypeScript, Vite, 
  Tailwind CSS, Zustand for state management, Framer Motion, and Lucide icons.
- Backend: REST API service built with Node.js (ESM), Express 5, and TypeScript.
- Database: PostgreSQL managed via Prisma ORM 7 with pooled connections (@prisma/adapter-pg).
- Cache & Session Store: Redis for 10-minute OTP staging and pre-flight registration caches.
- Media Storage: ImageKit for direct client uploads with backend authentication signatures.
- Email Service: Nodemailer with Gmail SMTP (App Password / OAuth2) and local dev terminal OTP fallback.
- Security: Dual JWT token architecture (Short-lived access token + HTTP-Only 7-day refresh token cookie),
  Bcrypt password hashing (salt rounds: 10), Role-Based Access Control (Owner, Admin, Member, Employee).

A. AUTHENTICATION & SESSION MANAGEMENT (/api/auth)
--------------------------------------------------------------------------------

1. POST /api/auth/registerVerification
   - Purpose: Pre-validates registration details against DB, stages data in Redis (10m TTL),
     and dispatches a 6-digit OTP to the user's email.
   - Auth Required: None (Public)
   - Data Entry Flow (Request Body):
     {
       "name": "Jane Doe",                   // String, required for new registration
       "email": "jane@example.com",          // String, required
       "password": "Password123!",           // String, required for new registration
       "registrationPath": "newOrg" | "existingOrg", // String, required
       "organisationName": "Acme Corp",      // String, required if registrationPath === "newOrg"
       "inviteToken": "org_inv_xxx"          // String, optional if registrationPath === "existingOrg"
     }
     * Note: If only {"email": "..."} is sent without name/password, it acts as Resend OTP.
   - Process:
     - Verifies email does not exist in User table.
     - If newOrg, verifies organisationName does not exist in Organisation table.
     - If existingOrg with inviteToken, verifies token is valid and unexpired.
     - Hashes password using bcrypt.
     - Stores staged payload in Redis: `pending_registration:<email>` (EX: 600s).
     - Generates 6-digit OTP via crypto.randomInt(100000, 1000000).
     - Stores OTP in Redis: `otp:<email>` (EX: 600s).
     - Dispatches email via Nodemailer.
   - Output (Success - 200 OK):
     {
       "statuscode": 200,
       "data": null,
       "message": "Verification successful. OTP sent to your email."
     }
   - Output (Error - 400 / 404 / 500):
     { "error": "User with this email already exists" }
     { "error": "Organisation already exists" }
     { "error": "Invalid invite token" }

2. POST /api/auth/registerWithNewOrganisation
   - Purpose: Verifies OTP via middleware and creates Owner User and new Organisation.
   - Middleware Chain: [registerVerification, otpVerification, registerWithNewOrganisation]
   - Auth Required: None (Public, verified via OTP)
   - Data Entry Flow (Request Body):
     {
       "email": "jane@example.com",          // String, required
       "inputOtp": "123456"                  // String, 6 digits, required
     }
   - Process:
     - registerVerification middleware checks if user already created.
     - otpVerification middleware checks `otp:<email>` in Redis matches inputOtp; deletes OTP upon match.
     - registerWithNewOrganisation retrieves `pending_registration:<email>` from Redis.
     - Creates User with Role "Owner" in DB.
     - Creates Organisation with ownerId = User.id in DB.
     - Associates User.organisationId = Organisation.id.
     - Deletes `pending_registration:<email>` from Redis.
     - Mints Access Token and Refresh Token; attaches Refresh Token as HTTP-Only cookie.
   - Output (Success - 201 Created):
     Set-Cookie: refreshToken=<jwt>; HttpOnly; Secure; SameSite=Strict; Max-Age=604800
     {
       "statuscode": 201,
       "data": {
         "accessToken": "eyJhbGciOi...",
         "user": {
           "id": "uuid-v4",
           "name": "Jane Doe",
           "email": "jane@example.com",
           "role": "Owner",
           "organisationId": "uuid-v4"
         }
       },
       "message": "New User registered and logged in successfully"
     }

3. POST /api/auth/newUserRegistration
   - Purpose: Verifies OTP via middleware and creates Employee user account (joining existing org if invited).
   - Middleware Chain: [registerVerification, otpVerification, newUserRegistration]
   - Auth Required: None (Public, verified via OTP)
   - Data Entry Flow (Request Body):
     {
       "email": "john@example.com",          // String, required
       "inputOtp": "123456"                  // String, 6 digits, required
     }
   - Process:
     - Verifies OTP in Redis; retrieves staged payload.
     - Creates User with Role "Employee" in DB.
     - If staged inviteToken was valid, links user to target Organisation.
     - Clears Redis staged data; mints session tokens.
   - Output (Success - 201 Created):
     Set-Cookie: refreshToken=<jwt>; HttpOnly; Secure; SameSite=Strict; Max-Age=604800
     {
       "statuscode": 201,
       "data": {
         "accessToken": "eyJhbGciOi...",
         "user": {
           "id": "uuid-v4",
           "name": "John Smith",
           "email": "john@example.com",
           "role": "Employee",
           "organisationId": "uuid-v4" | null
         }
       },
       "message": "New User registered and logged in successfully"
     }

4. POST /api/auth/login
   - Purpose: Authenticates an existing user via email and password.
   - Auth Required: None (Public)
   - Data Entry Flow (Request Body):
     {
       "email": "jane@example.com",          // String, required
       "password": "Password123!"           // String, required
     }
   - Process:
     - Looks up user by email.
     - Compares bcrypt passwordHash.
     - Mints Access Token (expires in ACCESS_TOKEN_EXPIRY, e.g. 1d).
     - Mints Refresh Token (expires in 7d); updates User.refreshToken in DB.
     - Sets HTTP-Only cookie `refreshToken`.
   - Output (Success - 200 OK):
     Set-Cookie: refreshToken=<jwt>; HttpOnly; Secure; SameSite=Strict; Max-Age=604800
     {
       "statuscode": 200,
       "data": {
         "accessToken": "eyJhbGciOi...",
         "user": {
           "id": "uuid-v4",
           "name": "Jane Doe",
           "email": "jane@example.com",
           "role": "Owner",
           "organisationId": "uuid-v4"
         }
       },
       "message": "Logged in successfully"
     }
   - Output (Error - 401 Unauthorized):
     { "error": "Invalid email or password" }

5. GET /api/auth/refresh
   - Purpose: Silently mints a new Access Token using the HTTP-Only refresh cookie.
   - Auth Required: HTTP-Only cookie `refreshToken`
   - Output (Success - 200 OK):
     {
       "statuscode": 200,
       "data": {
         "accessToken": "eyJhbGciOi...",
         "user": { "id": "uuid", "name": "...", "email": "...", "role": "...", "organisationId": "..." }
       },
       "message": "Session refreshed successfully"
     }
   - Output (Error - 401 Unauthorized):
     { "error": "No refresh token, please log in again" }

6. POST /api/auth/logout
   - Purpose: Terminates active user session and clears cookies.
   - Auth Required: Bearer Access Token
   - Output (Success - 200 OK):
     Clear-Cookie: refreshToken
     {
       "statuscode": 200,
       "data": {},
       "message": "Logged out successfully"
     }

7. GET /api/auth/verify
   - Purpose: Returns the currently authenticated user's profile and verifies token validity.
   - Auth Required: Bearer Access Token
   - Output (Success - 200 OK):
     {
       "statuscode": 200,
       "data": { "user": { "id": "...", "name": "...", "email": "...", "role": "...", "organisationId": "..." } },
       "message": "Session verified successfully"
     }

8. POST /api/auth/forgotPassword
   - Purpose: Step 1 of password recovery: verifies user email exists, generates 6-digit OTP,
     stores in Redis (10m TTL), and dispatches reset email.
   - Auth Required: None (Public)
   - Data Entry Flow (Request Body):
     {
       "email": "jane@example.com"           // String, required
     }
   - Process:
     - Checks user in DB (returns 404 if not found).
     - Generates 6-digit OTP.
     - Sets `forgot_otp:<email>` in Redis with 10-minute expiry (600s).
     - Sends OTP email via Nodemailer (with terminal console fallback in dev).
   - Output (Success - 200 OK):
     {
       "statuscode": 200,
       "data": null,
       "message": "Password reset OTP sent to your email."
     }
   - Output (Error - 404 Not Found):
     { "error": "User with this email does not exist" }

9. POST /api/auth/resetPassword
   - Purpose: Step 2 of password recovery: verifies OTP, hashes new password, updates DB,
     invalidates old sessions by setting refreshToken = null, and deletes Redis OTP.
   - Auth Required: None (Public, verified via OTP)
   - Middleware Chain: [forgotOtpVerification, resetPasswordWithOTP]
   - Data Entry Flow (Request Body):
     {
       "email": "jane@example.com",          // String, required
       "inputOtp": "123456",                 // String, 6 digits, required
       "newPassword": "NewSecretPassword123!"// String, min 6 chars, required
     }
   - Output (Success - 200 OK):
     {
       "statuscode": 200,
       "data": null,
       "message": "Password reset successfully. Please log in with your new password."
     }
   - Output (Error - 400 Bad Request):
     { "error": "Invalid OTP" }
     { "error": "OTP has expired or was not requested" }
     { "error": "New password must be at least 6 characters long" }

10. POST /api/auth/changePassword
    - Purpose: Authenticated password change for logged-in users who know their current password.
    - Auth Required: Bearer Access Token
    - Data Entry Flow (Request Body):
      {
        "oldPassword": "CurrentPassword123!", // String, required

    - Output (Success - 200 OK):
      {
        "statuscode": 200,
        "data": null,
        "message": "Password changed successfully"
      }
    - Output (Error - 400 Bad Request):
      { "error": "Incorrect current password" }

11. POST /api/auth/userOwnnerWithoutOrg

--------------------------------------------------------------------------------
PAGE 1: AUTHENTICATION (Login.tsx)
--------------------------------------------------------------------------------
Path: / (when unauthenticated)
Components / Segments:

- Segment 1: Tab Navigation Toggle
  - UI: SubSelectToggleDemo animated switch.
  - Options: "Login" | "Register".

- Segment 2: Login Form
  - Entries Offered:
    * Email Address (type: email, required)
    * Password (type: password, required, with show/hide Eye toggle)
    * "Forgot?" Button (triggers Segment 5: Forgot Password view)
    * "Access Dashboard" Action Button
  - State: isLoggingIn (shows loading spinner & disabled inputs)
  - Output: On success -> stores accessToken in memory, updates userData in Zustand store,
    sets currentPage to 'dashboard'.

- Segment 3: Register Form - New Organisation ("newOrg" Sub-tab)
  - Entries Offered:
    * Full Name (type: text, required)
    * Email Address (type: email, required)
    * Password (type: password, required, with show/hide Eye toggle)
    * Organisation Name (type: text, required)
    * "Create Account" Action Button
  - Action: Dispatches registerVerification payload to backend; upon 200 OK, transitions
    currentPage to 'otp'.

- Segment 4: Register Form - Existing Organisation ("existingOrg" Sub-tab)
  - Entries Offered:
    * Full Name (type: text, required)
    * Email Address (type: email, required)
    * Password (type: password, required, with show/hide Eye toggle)
    * Invite Token (type: text, optional - can also join later)
    * "Register & Join" Action Button
  - Action: Dispatches registerVerification payload; transitions currentPage to 'otp'.

- Segment 5: Forgot Password View
  - Trigger: Clicking "Forgot?" in the login form.
  - Entries Offered:
    * "Back to Sign In" Action Button (returns to Login form)
    * Email Address (type: email, required)
    * "Send Verification Code" Action Button (shows Loader2 when isSendingForgotMail is true)
  - Action: Calls userStore.sendForgotPasswordMail(email). Upon success, stores email in
    sessionStorage (otp_mode = "forgot_password") and sets currentPage to 'otp'.

PAGE 2: OTP VERIFICATION (otp.tsx)
--------------------------------------------------------------------------------
Path: Controlled via userStore.currentPage === 'otp'
Components / Segments:

- Segment 1: Header & Context
  - Dynamic Display:
    * Registration Mode: "Verification Code" | "We have sent a 6-digit OTP code to <email>"
    * Forgot Password Mode: "Reset Verification" | "We have sent a 6-digit password reset OTP code to <email>"
  - "Back" Button: cleans up staging session and returns to login.

- Segment 2: 6-Digit OTP Input Grid
  - 6 individual numeric input fields.
  - Auto-advance to next box on input; backspace jumps to previous box.
  - Paste listener: parses complete 6-digit string from clipboard and fills all boxes.

- Segment 3: Verification Action Button
  - Dynamic Button Text:
    * Registration Mode: "Verify Code & Register" (calls verifyOTPAndRegister)
    * Forgot Password Mode: "Verify Code & Continue" (stores pending_reset_otp and sets currentPage to 'reset-password')
  - Loading State: Shows spinner during network verification.

- Segment 4: Resend OTP Countdown
  - 30-second cooldown timer.
  - When timer reaches 0: displays clickable "Resend Code" button.
  - Action: re-dispatches OTP based on current otp_mode.
